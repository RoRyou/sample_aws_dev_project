# AWS 実践計画：商品カタログ API をゼロから作る

作成日: 2026-09-20

> 目標：**全工程を自力で完了する。AI にコードを書かせたりデバッグさせたりしない。**
> 本文書はルート、チェックポイント、受け入れ基準のみを提供する。

作るのは、自分のリポジトリにゼロから書く商品カタログ API。
[aws-samples/sample-aws-developer-project](https://github.com/aws-samples/sample-aws-developer-project) は
**参照アーキテクチャ（お手本）として読むだけ**で、コードはコピーしない。

---

## 1. このプロジェクトとは

参照サンプルの設計思想は、**5 つの異なるアーキテクチャで同じ業務を繰り返し実装する**こと。題材は商品カタログ API。

業務が単純なのは意図的。フェーズを切り替えるたびに、意識が「AWS のサービスとアーキテクチャの何が変わったか」に集中する。

| # | フェーズ | AWS サービス | 前のフェーズからの追加分 |
| --- | --- | --- | --- |
| 1 | 最小の API | Lambda、API Gateway | 出発点：データはメモリ上、再起動で消失 |
| 2 | 永続化 | + DynamoDB | データの永続化 |
| 3 | 本格構成 | + VPC、ElastiCache、Cognito、S3、DynamoDB Streams | キャッシュ、認証、ファイルアップロード、イベント駆動 |
| 4 | コンテナ版 | ECS Fargate、ALB、VPC | 別ルート：Lambda でなくコンテナで同じ API |
| 5 | 自動化 | CodePipeline / GitHub Actions | デプロイの自動化 |

最初の 3 つは一本の線で層を重ねる。4 つ目は**横の比較**。同じ API をサーバーレスとコンテナで実装し、
コード構成・コスト・コールドスタート・運用の違いを見る。本プロジェクトで最も価値のある部分の一つ。

### 技術スタック

- **Python 3.12+** で Lambda 関数とコンテナ内の Flask アプリを記述
- **AWS CDK (Python)** でインフラを記述
- **AWS CLI v2** でコマンドライン検証
- **pytest / moto** で単体テスト。moto は AWS サービスを mock し、ローカルで完結
- **Docker** でコンテナイメージをビルド（フェーズ 4 のみ）

### 参照サンプルを読むときの注意

このリポジトリは非常に新しく、**ほぼメンテナンスされていない**。コミットは計 3 件
（2026-01-27 初期化、2026-01-30 ファイル名変更）で以降更新なし。star 3、fork 7。

これは 2 つのことを意味する：

1. 問題に当たっても **Google で他人の事例が見つからない**。コード、AWS 公式ドキュメント、
   エラーメッセージを自分で読むしかない。「AI を使わず自力で」という目標にとってはむしろ好都合。
2. リポジトリに**既存のバグがある**（〈フェーズ 0〉参照）。
   「公式リポジトリが動かないのは自分のせい」と決めつけないこと。

## 2. 最終的に得られるもの

5 つのフェーズを完走したとき、**調べなしで**下記ができるようになっているはず。
これが各フェーズの受け入れ基準でもある。

### スキル一覧

- CDK で Stack をゼロから書く（Lambda、API Gateway、DynamoDB を含む）、デプロイを成功させる
- `cdk synth` が生成する CloudFormation テンプレートを読み、CDK の 1 行がどのリソースに展開されるかを把握する
- コンソールではなく AWS CLI で、照会・呼び出し・ログ閲覧・設定変更を行う
- Lambda がエラーを出したとき、CloudWatch Logs のどの log group を見ればスタックトレースがあるか分かる
- 説明できる：VPC 内の Lambda が外部に出られない理由、Security Group で ElastiCache への通信を許可する方法
- 説明できる：S3 署名付き URL でフロントがバックエンドを経由せず直接アップロードできる仕組み
- 説明できる：同じ API を Lambda と Fargate で実装した場合、コスト曲線がどのトラフィック量で交差するか
- アーキテクチャ一式の月額請求を見積もり、どのリソースが支配的かを言える

### 成果物

進めながら作っていくことを推奨。終わったときに実際の学習記録が残る：

- [ ] 自分のトラブルシューティングノート：15 分以上詰まった問題ごとに、エラー原文 + 最終的な原因 + 修正内容
- [ ] フェーズ 3 のアーキテクチャ図（手書き可）。コードを見ずに再現できること
- [ ] 5 フェーズのコスト比較表。数字は価格表ではなく自分の請求から
- [ ] 参照リポジトリへの PR を最低 1 本（フェーズ 0 のバグがそのまま素材になる）

### このプロジェクトの範囲外

期待値をずらさないために明記する。本プロジェクトは**扱わない**：
本番レベルのマルチ環境管理、IAM 権限の精緻な設計、監視・アラート体制、マルチリージョン DR、コスト最適化の実践。

また、参照サンプルは**ベストプラクティスの見本ではない**。作法が雑な箇所がいくつかあるので、読むときは批判的に。

## 3. 着手前の準備

所要 1〜2 時間。AWS アカウントの有効化待ちが大半を占める。**前日に済ませておく**ことを推奨。

### 3.1 個人 AWS アカウントを作る（重要）

ローカルの `~/.aws/config` には現在会社のアカウント（`ai-agent-base` の dev / stg / prd）しかなく、
`default` profile のトークンは失効している。

**実践には別途個人アカウントを使うこと：**

- `cdk bootstrap` はアカウント単位の変更（CDKToolkit の S3 bucket、ECR、IAM role を作成）
- VPC / ElastiCache / Cognito / ALB などが会社環境に混在し、請求も会社持ちになる
- デプロイには管理者に近い権限が必要で、会社の `developers-role` では AccessDenied にはまる可能性が高い。
  それは AWS の学習ではなく権限との格闘

リージョンは `us-east-1`。ドキュメントの例がすべてこれを前提に書かれており、無料枠とサービスのカバレッジも最も広い。

### 3.2 専用 profile を用意する

`default` は触らず、`personal-lab` などの名前で新規作成する。
以降のコマンドはすべて `--profile personal-lab` を明示し、会社アカウントへの誤操作を防ぐ。

習慣にすること：**作業開始時の最初のコマンドは `aws sts get-caller-identity --profile personal-lab`**。
account ID が個人アカウントであることを確認してから着手する。

### 3.3 ツール確認

ローカル環境の現状は確認済み：

| ツール | 現在のバージョン | 状態 |
| --- | --- | --- |
| AWS CLI | 2.31.30 | OK |
| Node.js | v24.5.0 | OK |
| Docker | 29.1.3 | OK（フェーズ 4 で使用） |
| Python | 3.14.7（デフォルト） | **新しすぎる。使わない** |
| AWS CDK CLI | 未インストール | `npm install -g aws-cdk` が必要 |

**Python のバージョンは落とし穴。** デフォルトの `python3` は 3.14.7 だが、CDK が依存する jsii の 3.14 対応は不確実。
venv には `/opt/homebrew/bin/python3.13` を使う。

### 3.4 リポジトリとドキュメントの配置

自分のリポジトリをゼロから作る。初期構成はこの程度で十分：

```
my-aws-catalog/
├─ README.md            ← この計画書
├─ .gitignore           ← .venv, cdk.out, __pycache__ を除外
├─ app.py               ← フェーズ 0 で cdk init が生成
└─ docs/
   └─ troubleshooting.md  ← 詰まった記録を貯めていく
```

中国語版の計画書はリポジトリ外にローカル保持する。

フェーズごとにブランチを切って進め、完了時に main へマージすると、後から学習の軌跡を辿れる。

### 3.5 予算アラートを設定する（着手前必須）

AWS Billing コンソールで **月額 $10** の Budget アラートをメール通知付きで作成する。
正常に進めればここまでかからないが、削除忘れ時のセーフティネットになる。

あわせて **Free Tier usage alerts** も有効にしておく。

## 5. フェーズ 1：最小の API を自分で書く

**見積 4〜5 時間 · コスト ほぼ $0（無料枠内）**

Lambda + API Gateway で商品カタログ API を書く。データはメモリ上で構わない。
本当の目的は「デプロイ成功」ではなく、**デプロイ → 検証 → 破棄のループを体に覚えさせる**こと。

### 自分で設計するところ

コードを書く前に、紙の上で決める。**この設計作業がコピーとの最大の差：**

- エンドポイントの設計（`GET /products`、`POST /products`、`GET /products/{id}` など）
- 商品のデータ構造（id、name、price、category など）
- Lambda をエンドポイントごとに分けるか、1 つにまとめるか。それぞれの利点は？
- エラー時のレスポンス形式を統一する

決めたら README に書いてから実装に入る。

### タスク

- [ ] API 仕様を決めて README に記述
- [ ] Lambda ハンドラを自分で書く
- [ ] CDK で Lambda と API Gateway を定義
- [ ] `cdk bootstrap`（アカウント単位、初回のみ）→ `cdk deploy`
- [ ] `curl` で全エンドポイントを叩く
- [ ] 意図的にエラーを起こし、CloudWatch Logs でそのログを見つける
- [ ] `aws lambda invoke` で API Gateway を経由せず直接呼び、入力イベントの形を比べる
- [ ] `cdk destroy` → CLI でリソース消滅を確認
- [ ] フェーズ 1 をコミット

### コンソールではなく CLI を使う

このフェーズの必須条件。コンソールで数回クリックすれば見えるものも、あえてコマンドで確認する：

- `aws lambda list-functions`
- `aws apigateway get-rest-apis`
- `aws logs tail <log-group> --follow`
- `aws cloudformation describe-stack-resources --stack-name <name>`

コンソールを 1 週間使っても記憶に残らないが、CLI は 3 回叩けば覚える。実務で使うのも CLI。

### 受け入れ基準

何も見ずに、空のディレクトリから最小の CDK Stack（Lambda 1 つ + API Gateway、`hello world` を返す）を書き、
デプロイして破棄できること。書けなければ、書けるようになるまで繰り返す。ここが全フェーズの土台。

## 6. フェーズ 2：DynamoDB で永続化する

**見積 5〜6 時間 · コスト ほぼ $0（リクエスト課金、実践量では無視できる）**

メモリ上のデータを DynamoDB に移す。自分で書く場合、ここが最初の本格的な設計判断になる。

### 先にテーブル設計を決める

DynamoDB は **アクセスパターンから逆算して設計する**データベース。RDB のつもりで書くと必ず行き詰まる。

実装前に紙に書き出す：

1. この API はどんなクエリを投げるか（ID 検索、全件取得、カテゴリ別…）
2. それぞれのクエリに対して partition key / sort key をどう取るか
3. GSI が必要なクエリはどれか

### タスク

- [ ] テーブル設計を決め、根拠を README に残す
- [ ] CDK で DynamoDB テーブルを定義（`PAY_PER_REQUEST`、`RemovalPolicy.DESTROY`）
- [ ] Lambda から boto3 で読み書きするコードを自分で書く
- [ ] Lambda に必要最小の IAM 権限だけ与える（`table.grant_read_write_data(fn)`）
- [ ] `moto` で単体テストを書く。AWS にデプロイせずにロジックを検証する
- [ ] デプロイし、`curl` でデータが残ることを確認
- [ ] `aws dynamodb scan` / `query` で生データを直接見る
- [ ] `cdk destroy` → コミット

### つまずきやすい点

自分で書くと必ずここで止まる。先に知っておく：

- **`float` が保存できない。** DynamoDB は `Decimal` を要求する。なぜかを調べること
- **`scan` と `query` の違い。** なぜ本番で `scan` が忌まれるか
- **partition key の偏り。** ホットパーティションとは何か
- **IAM 権限不足。** `AccessDeniedException` が出たら、どのロールに何のアクションが足りないのかをメッセージから読み取る練習を

### 受け入れ基準

「カテゴリ別に商品を検索したい」と言われたとき、現在のテーブル設計をどう変えるか即答できること。
SQL の `WHERE category = 'x'` がなぜそのままは使えないのかも説明できること。

## 7. フェーズ 3：本格構成を組み上げる（中核）

**見積 14〜18 時間 · コスト 約 $0〜12/月（ElastiCache の無料枠次第）**

VPC、ElastiCache、Cognito、S3、DynamoDB Streams を組み上げる。
**全工程で最も難しく、最も学べる区間。時間はフェーズ 1・2 の合計より多く取ること。**

ゼロから書く場合、ここだけは参照サンプルの `full_api_stack.py`（432 行）を読む価値がある。
ただし**読んでから閉じて、自分の言葉で書き直す**こと。

### 必ず分割して進める

一気に全部をデプロイすると、失敗時にどこが原因か全く分からない。この順で、毎回単体で検証する：

| サブ | 内容 | 時間 | 検証方法 |
| --- | --- | --- | --- |
| 3a | VPC を自分で定義する | 3h | サブネット・ルートテーブル・SG の図を描ける |
| 3b | S3 署名付き URL | 3h | `curl` で画像を直接 S3 にアップロード |
| 3c | Cognito 認証 | 4h | token を取得し、保護 API を呼べる |
| 3d | ElastiCache キャッシュ | 3h | ヒット時とミス時の応答時間を比較 |
| 3e | DynamoDB Streams | 2h | 価格を変更し、発火した Lambda のログを見る |

各サブをブランチに分け、動いたらマージする。

### ここで詰まるもの

先に伝えておく。詰まったときに考える方向が分かる：

- **VPC 内の Lambda が外に出られない。** NAT Gateway は高額（月約 $32）なので使わない。
  では DynamoDB にどう接続するか。キーワードは VPC Endpoint
- **Security Group の設定ミスで ElastiCache に繋がらない。** 最頻出の詰まりどころ。
  インバウンドとアウトバウンドの理解が問われる
- **Cognito のコールバック URL 不一致。** ドメインプレフィックスはグローバルに一意である必要がある点にも注意
- **Lambda Layer のビルド。** redis や Pillow のようなネイティブ拡張を含む Layer は、
  **Linux 環境でビルドしなければならない**。macOS で作った `.zip` は Lambda 上で動かない。これは必ず一度踏む

### タスク

- [ ] 3a〜3e を順に設計・実装・検証
- [ ] アーキテクチャ図を描く（〈成果物〉の 1 つ）
- [ ] キャッシュの実測値（ミリ秒）を記録する
- [ ] **その日の作業後は必ず `cdk destroy`**（ElastiCache は時間課金）

### 受け入れ基準

AWS 未経験の人に向かって、自分の描いた図を使い、「認証付きの商品画像アップロード」が
どのサービスをどの順で通るかを最初から最後まで説明できること。

## 8. フェーズ 4：コンテナ版を作って比較する

**見積 6〜7 時間 · コスト 約 $0.60/日（ALB は無料枠外）**

同じ API を ECS Fargate + ALB で実装する。Lambda とは別ルート。

### コスト警告

**全工程で唯一、削除を忘れると課金が続くフェーズ。**
ALB は月約 $16〜18（時間単位で約 $0.025/h）で、トラフィックの有無に関わらず課金される。

推奨：**半日で集中して終わらせ、その日のうちに destroy**。
分割する場合も、作業終了毎に destroy し、次回再デプロイする（約 5〜10 分）。

### タスク

- [ ] Flask（または FastAPI）で同じ API を実装する
- [ ] `Dockerfile` を自分で書く。ローカルで `docker build` → `docker run` で動作確認
- [ ] CDK で ECS Fargate サービスと ALB を定義
- [ ] デプロイし、ALB の DNS 名で API にアクセス
- [ ] `aws ecs describe-services` で状態、`aws logs tail` でコンテナログを見る
- [ ] タスク数を 2 に変えて再デプロイし、ALB の振り分けを観察
- [ ] **その日のうちに destroy。EC2 コンソールで ALB 消滅を目視確認**

### このフェーズの本当の価値：横の比較

「動いた」で終わらせない。同じ業務の 2 つの実装を並べて比較する：

| 観点 | Lambda 版 | Fargate 版 |
| --- | --- | --- |
| コード構成 | エンドポイントごとに関数 | 1 つのアプリにルーティング |
| コールドスタート | あり | なし（常駐） |
| アイドル時コスト | ほぼ 0 | ALB + タスクが継続課金 |
| 適する場面 | トラフィックが疎・スパイク状 | トラフィックが安定・継続的 |
| ローカルデバッグ | 面倒 | `docker run` で完結 |

自分で計算してみる：**月間リクエスト数がいくつで両者のコストが逆転するか。**
この数字を出せれば、両アーキテクチャの理解が定着する。

### 受け入れ基準

どんな要件なら Fargate を選び、どんな要件なら Lambda を選ぶか。
理由を 3 つ以上、自分で出したコストの数字付きで説明できること。

## 9. フェーズ 5：デプロイを自動化する

**見積 4〜5 時間 · コスト 約 $1/月（CodePipeline）**

ここまで手で実行してきた `cdk deploy` を、push で自動発火させる。

### 優先度は最低

率直に言うと、時間がなければ**このフェーズは飛ばしてもよい**。理由：

- CI/CD は概念的な要素が大きく、手を動かすことで得られるものが相対的に少ない
- 実務では CodePipeline より GitHub Actions を使うチームが多く、知識の転用が効きにくい
- フェーズ 1〜4 の理解に影響しない

### 代替案：GitHub Actions でやる

リポジトリが GitHub にあるなら、**CodePipeline ではなく GitHub Actions で組む方が実用的**。
学べることは多く重なる：

- OIDC で AWS に認証する（アクセスキーをリポジトリに置かない方法）
- PR で `cdk diff`、main マージで `cdk deploy`
- デプロイ用 IAM ロールの権限設計

OIDC 認証は実務でそのまま使える知識で、CodePipeline より価値が高い。

### タスク

- [ ] どちらかを選んでパイプラインを組む
- [ ] push して自動実行を確認
- [ ] 意図的にビルドが失敗するコミットを push し、ログの読み方を覚える
- [ ] パイプラインがどの権限で動いているかを説明できるようにする
- [ ] 不要なリソースを destroy

### 受け入れ基準

選んだ方の仕組みについて、もう一方と比べた利点と欠点をそれぞれ 1 つ以上述べられること。

## 10. 所要時間とスケジュール

**集中時間の合計 37〜46 時間。** 開発経験はあるが AWS は初めて、AI の助けを借りない前提での見積もり。

サンプルをデプロイするだけなら 28〜38 時間だが、**ゼロから自分で書く分だけ約 1.3 倍になる**。
その差分がこの進め方の価値。

## 11. コスト管理

**真面目に運用すれば全工程で $5 以内。削除を忘れると 1 ヶ月で $30 を超える。**

自分で VPC を書くときは、**NAT Gateway を作らない**ことを意識する。
CDK の `Vpc` はデフォルトで NAT Gateway を作り、月約 $32 かかる。`nat_gateways=0` を明示する。

### 課金ポイント

| リソース | フェーズ | 課金 | リスク |
| --- | --- | --- | --- |
| NAT Gateway | 3（作らない） | 月約 $32 | **最大の罠。必ず `nat_gateways=0`** |
| ALB | 4 | 月約 $16〜18 | 高——唯一の継続課金 |
| ElastiCache `cache.t3.micro` | 3 | 新規アカウントは 12 ヶ月間 750h/月無料、以降 月約 $12 | 中 |
| CodePipeline | 5 | 月約 $1 | 低 |
| Lambda / API Gateway / DynamoDB / S3 / Cognito | 1〜3 | 無料枠内でほぼ 0 | なし |

### 作業終了時のチェック（習慣化する）

手を止めるたびに実行する。1 分かからない：

- [ ] `cdk destroy --all --profile personal-lab`
- [ ] `aws cloudformation list-stacks --stack-status-filter CREATE_COMPLETE UPDATE_COMPLETE --profile personal-lab` — 残るのは `CDKToolkit` のみ
- [ ] フェーズ 4 をやった日は追加で：`aws elbv2 describe-load-balancers --profile personal-lab` が空であること

### 週次チェック

Billing コンソールの Cost Explorer を一目見て、数字が想定通りか確認する。
意外な課金があれば、サービス別にグループ化すれば、どのリソースの消し残しかすぐに特定できる。

### destroy が失敗したとき

よくあるのは、S3 bucket が空でなく `cdk destroy` が止まるケース。先に bucket を空にしてから再実行する。

どうしても消せない場合は CloudFormation コンソールから手動で Stack を削除し、
引っかかるリソースは Retain でスキップしてから個別に片付ける。

**消せないリソースを放置しないこと。**

## 12. 詰まったときの対処

AI を使わない以上、代替の手順が必要。順番にやる。**飛ばさないこと：**

1. **エラーを最後まで読む。** AWS のエラーは長いが、決め手はその中に書いてあることが多い。1 行目だけで判断しない
2. **本当のログを探す。** CDK のエラー → CloudFormation のイベント、Lambda のエラー → CloudWatch Logs。
   エラーが見える場所と原因の場所は違う
3. **公式ドキュメントを引く。** 入口は下記
4. **ソースを読む。** CDK は OSS で、`aws-cdk-lib` の Python コードは venv の中にある。定義に飛んで直接見る
5. **最小再現を作る。** 問題のリソースだけの Stack を新規に作り、ノイズを落とす。最も効果的で、最も飛ばされやすい手順
6. **一日置く。** 2 時間詰まったら止める。翌日 5 分で解けることがよくある

### 公式資料

| 資料 | 用途 |
| --- | --- |
| [AWS CDK API Reference](https://docs.aws.amazon.com/cdk/api/v2/python/) | コンストラクトの引数を調べる。最頻繁 |
| [AWS CDK Developer Guide](https://docs.aws.amazon.com/cdk/v2/guide/home.html) | 概念（Aspects、Context、環境） |
| [AWS CLI Command Reference](https://docs.aws.amazon.com/cli/latest/reference/) | コマンドとパラメータ |
| [CDK Patterns](https://cdkpatterns.com/) | 同種の構成を他人がどう書いているか |
| [参照サンプルの docs/](https://github.com/aws-samples/sample-aws-developer-project/tree/main/docs) | 10 本。各篇にトラブルシューティング章あり |

### トラブルシューティングノートを作る

15 分以上詰まった問題は、毎回 3 行で記録する：

```
エラー：<原文のまま。意訳しない>
原因：<最終的に分かったこと>
対処：<具体に何を変えたか>
```

リポジトリの `docs/troubleshooting.md` に置いてコミットしていくと、フェーズ 3 に入ったときに非常に効いてくる。
同じミスは繰り返す。

### AI を使ってもよい場面

AI を使わないのは能力を作るためであって、苦行のためではない。目安：

- **上記 6 歩を試したうえで一日以上詰まった** → 方向だけ聞く（「このエラーはどの辺りの問題か」）。コードはもらわない
- **フェーズ完了後** → 自分の理解をレビューしてもらう。学習効果は下がらない
- **コードを書く工程** → 自分で書く。これがこの計画の中核

詰まること自体が学習。能力になるのは、自分で抜け出した瞬間。
